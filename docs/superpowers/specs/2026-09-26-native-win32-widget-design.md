# DesktopTodoList 原生 Win32 桌面组件设计

**日期：** 2026-09-26
**状态：** 已确认
**目标版本：** v2.0 原生桌面版

## 1. 背景与决策

DesktopTodoList 当前实现以 HTML/CSS/JavaScript 为界面、PowerShell 为宿主，并由 Edge 应用模式承载。该方案虽然能够模拟无边框浮窗，但本质上仍是浏览器应用，不符合“桌面上直接悬浮的小插件”的产品定位。

本次设计将运行时整体替换为纯原生 Windows 程序：

- 使用 C++20、Win32、Direct2D、DirectWrite 和 Windows Runtime API。
- 运行时不启动 Edge、浏览器、本地 HTTP 服务或 PowerShell。
- 交付可直接运行的 `.exe`、按用户安装的安装程序，以及便携版压缩包。
- 分别生成 x64 与 ARM64 构建。
- 保留既有业务需求、数据结构和行为语义，仅替换表现层、宿主层及分发方式。

旧 HTML/Edge 版本保留在 Git 历史中，不再作为新版本的运行时组成部分。

## 2. 需求边界

### 2.1 保持不变

- 任务新增、编辑、完成、删除、撤销、详情、搜索和排序。
- 今天、本周、全部、已完成视图及统计。
- 提醒、补提醒、提前提醒与去重语义。
- 单选、多选、连续选择、框选和批量操作。
- 深浅主题、快捷键、托盘、开机自启和全局唤起。
- 浮窗、置顶、置底、鼠标穿透及逃生机制。
- 离线优先、无遥测、无业务数据上传。
- Windows 10 1809+、Windows 11、x64、ARM64和高 DPI 支持。
- 冷启动不超过 1 秒、1000 条任务渲染不超过 200 毫秒。
- 分发体积目标小于 5 MB；若安装器元数据或签名导致安装包略高，便携版程序仍必须满足该目标，并在发布验收中单独记录安装包体积。

### 2.2 被本设计替代的实现约束

需求文档中的以下内容属于旧方案实现细节，由本设计替代：

- Edge/Chromium 渲染内核要求。
- PowerShell 5.1、`launcher.ps1`、`window.ps1` 和本地静态服务器。
- `localStorage` 作为主存储。
- `启动待办.bat` 作为主要启动入口。
- “删除目录即卸载”不再是安装版的唯一卸载方式；安装版提供卸载程序，便携版仍可删除目录完成卸载。

## 3. 总体架构

应用为单一原生进程，内部按职责分为五层：

```text
Presentation
    ↓
Application
    ↓
Domain
    ↑
Persistence        Platform
```

### 3.1 Domain

纯 C++ 业务层，不依赖窗口句柄或绘图 API，包含：

- 任务、标签、优先级、截止时间和提醒状态模型。
- 智能视图筛选、排序和搜索。
- 单选、多选、锚点和不可见选中项规则。
- 提醒判断、补提醒、提前提醒和去重规则。
- schema 迁移后的业务校验。

该层通过独立测试程序执行单元测试，确保界面替换不改变业务语义。

### 3.2 Application

用例编排层，负责：

- 新增、编辑、完成、删除和批量操作。
- 五秒撤销窗口。
- 导入、导出、合并与覆盖事务。
- 自动保存调度、备份调度和提醒调度。
- 将领域事件转换为界面刷新和平台通知请求。

### 3.3 Persistence

持久化层使用 Windows 自带 API 与 JSON 格式，不引入第三方运行时。

默认数据位置：

```text
%LOCALAPPDATA%\DesktopTodoList\data.json
%LOCALAPPDATA%\DesktopTodoList\backups\YYYY-MM-DD.json
%LOCALAPPDATA%\DesktopTodoList\logs\desktop-todo-list.log
```

写入流程：

1. 在同一目录写入临时文件。
2. 刷新文件缓冲区。
3. 使用原子替换更新主文件。
4. 保留最近七个按日期生成的备份。
5. 写入失败时保留原文件并向用户显示可操作的错误。

读取流程：

1. 校验主数据 JSON 和 schema。
2. 主数据失败时从最新备份向前尝试。
3. 恢复成功后先保留损坏原件，再生成新的主数据。
4. 全部失败时进入空白安全状态，允许导出损坏文件，不静默覆盖。

原生版本继续使用 `schemaVersion: 1` 的逻辑结构。旧版导出的 JSON 可直接导入。旧 Edge 配置中的 `localStorage` 不作为新程序的隐式依赖；迁移通过旧版导出文件完成，后续可提供单独的显式迁移工具，但不得把浏览器运行时带回主程序。

### 3.4 Platform

平台层封装所有 Windows 集成：

- 单实例互斥量与第二实例唤起。
- 通知区域图标和上下文菜单。
- Windows Toast 通知及托盘气泡降级。
- `RegisterHotKey` 全局快捷键。
- `HKCU` 开机自启。
- 窗口层级、穿透、非激活和工作区定位。
- 系统主题、高对比度、DPI 和显示器变化监听。

第二实例不修改数据，只向已有实例发送“显示窗口”或“导入文件”请求后退出。

### 3.5 Presentation

表现层使用 Win32 窗口、Direct2D 和 DirectWrite：

- Direct2D 绘制背景、卡片、选中态、图标、阴影和动画。
- DirectWrite 绘制 Segoe UI Variable、Segoe UI 与 Microsoft YaHei UI 字体。
- 文本输入采用原生编辑控件或可访问的原生输入承载，保证输入法、剪贴板和屏幕阅读器兼容。
- 长列表使用视口虚拟化，仅布局和绘制可见任务及缓冲区。
- 交互元素暴露键盘焦点、可访问名称、状态与操作。
- `prefers-reduced-motion` 对应为系统“显示动画”设置，关闭时禁用非必要动画。

## 4. 窗口与悬浮组件行为

### 4.1 默认形态

- 程序启动后直接显示 `360 × 480` 的无边框悬浮组件。
- 默认不显示任务栏按钮，常驻通知区域。
- 支持紧凑和展开布局，两者使用同一个原生窗口。
- 关闭按钮默认收进托盘；设置为“退出”时才结束进程。

### 4.2 拖动、缩放与位置恢复

- 自绘顶部区域通过命中测试支持拖动。
- 窗口边缘保留缩放命中区，最小宽度 320 像素。
- 保存逻辑位置、逻辑尺寸和显示器标识。
- DPI 或显示器变化后按工作区重新约束，保证至少有可操作区域留在屏幕内。
- 125%、150% 和 200% DPI 下使用逻辑像素重新布局，不拉伸位图界面。

### 4.3 层级模式

置顶、普通、置底三个状态互斥：

- 置顶：使用 `HWND_TOPMOST`。
- 普通：使用 `HWND_NOTOPMOST`。
- 置底：使用底层 Z 序并禁止因普通点击意外升层；监听前台窗口变化时重新校正。

切换层级立即更新状态和托盘菜单，并持久化设置。

### 4.4 鼠标穿透

穿透状态组合使用分层、透明和非激活扩展样式。进入前显示一次明确提示，并始终保留至少以下两条恢复通道：

- `Ctrl+Alt+L` 全局切换。
- 托盘菜单“允许交互”。
- 可选的 30 分钟自动恢复。

穿透时托盘提示文字必须明确显示当前状态。恢复交互后，列表选择状态保持不变。

### 4.5 托盘与通知

托盘菜单至少包含：

- 显示/隐藏。
- 新建任务。
- 置顶/普通/置底。
- 允许交互。
- 设置。
- 退出。

安装版通过开始菜单快捷方式和应用标识支持 Windows Toast。便携版无法可靠注册 Toast 时，降级为托盘气泡与组件内提示。通知失败不得影响提醒去重状态的正确性。

## 5. 数据与兼容策略

### 5.1 数据结构

任务、设置和提醒字段沿用现有 schema 语义。运行时选择集合不写入业务数据。窗口模式、位置和主题等设置继续持久化。

### 5.2 导入导出

- 导出生成 UTF-8 JSON，不包含本机绝对路径。
- 导入前完整解析并校验，不边读边修改当前数据。
- 合并模式按任务 ID 合并并处理冲突。
- 覆盖模式先验证成功并备份当前数据，再一次性替换。
- 拖入 `.json` 文件等价于打开导入确认流程。

### 5.3 并发与崩溃安全

- 单实例机制避免两个进程同时写入。
- 保存采用短时防抖，但退出前执行最后一次同步保存。
- 崩溃恢复只读取已完成的主文件或备份，不采用未完成临时文件。
- 日志只记录程序状态和错误代码，不记录任务标题、备注等业务内容。

## 6. 构建、安装与发布

### 6.1 构建产物

每个版本生成：

```text
DesktopTodoList-x64.exe
DesktopTodoList-arm64.exe
DesktopTodoList-x64-Setup.exe
DesktopTodoList-arm64-Setup.exe
DesktopTodoList-x64-portable.zip
DesktopTodoList-arm64-portable.zip
checksums.txt
```

### 6.2 安装行为

- 默认安装到当前用户的本地应用目录，不请求管理员权限。
- 创建开始菜单快捷方式、卸载入口和 Toast 所需应用标识。
- 开机自启仅在用户主动打开设置后写入 `HKCU`。
- 卸载程序默认保留个人任务数据，并提供“同时删除个人数据”选项。
- 便携版无需安装；删除程序目录即可移除程序，但默认业务数据仍位于本地应用数据目录。

### 6.3 GitHub Releases

GitHub Actions 在 Windows 构建环境中执行：

1. 编译 x64 与 ARM64 Release。
2. 运行领域、持久化和平台纯函数测试。
3. 运行静态检查和分发内容检查。
4. 生成安装程序与便携包。
5. 计算 SHA-256 校验值。
6. 对版本标签构建上传全部产物到 GitHub Releases。

应用运行时不检查更新、不访问 GitHub，保持完全离线。

代码签名作为可选发布阶段：若仓库配置签名证书，则对程序和安装包签名；未配置时允许生成未签名开发发布，但发布说明必须提示 SmartScreen 可能显示“未知发布者”。

## 7. 源码布局

```text
native/
  CMakeLists.txt
  app/                  # 入口、生命周期、依赖组装
  domain/               # 纯业务模型与规则
  application/          # 用例和事件协调
  persistence/          # JSON、原子保存、备份和迁移
  platform/windows/     # 托盘、通知、热键、注册表、窗口层级
  presentation/         # 主窗口、控件、布局、绘制、主题
  resources/            # 图标、清单、版本信息和本地化字符串
  tests/                # 原生单元与集成测试
installer/              # 安装脚本和发布资源
.github/workflows/      # CI 与 Release 工作流
```

旧的 `src/`、`host/` 和 JavaScript/PowerShell 测试在迁移验收完成前保留作为行为参考。原生功能达到等价并通过验收后，再通过单独提交移出活动源码，不直接改写历史。

## 8. 测试与验收

### 8.1 自动测试

- 领域模型、筛选、排序、提醒、多选和撤销。
- JSON 校验、版本迁移、原子写入与七日备份。
- 合并和覆盖导入的事务性。
- 窗口状态转换、层级互斥和穿透逃生规则的纯函数部分。
- 1000 条任务布局和筛选性能基准。
- 安装包内容、架构、体积、校验值和禁止网络依赖检查。

### 8.2 Windows 人工验收

分别在 Windows 10 1809+ 与 Windows 11、x64 与 ARM64 环境验证：

- 冷启动、单实例、托盘和关闭行为。
- 置顶、普通、置底和鼠标穿透。
- 全局快捷键、开机自启和系统通知。
- 125%、150% 和 200% DPI，多显示器断开与重连。
- 安装、升级、卸载和数据保留选项。
- 输入法、键盘导航、高对比度与屏幕阅读器基本可用性。

无法在当前环境执行的系统级验收必须明确标为“待对应环境验收”，不能由模拟测试替代。

## 9. 迁移顺序

1. 建立 CMake、资源和测试骨架。
2. 移植 schema、领域模型与现有业务规则。
3. 实现原子持久化、备份、导入导出和旧 JSON 兼容。
4. 建立原生主窗口、布局、主题、输入和虚拟列表。
5. 接入任务操作、选择、拖动、详情和设置。
6. 接入托盘、热键、自启、层级、穿透和通知。
7. 完成安装脚本、双架构 CI 和 GitHub Releases。
8. 对照需求逐项验收后，停用旧 HTML/PowerShell 活动源码。

每个阶段必须先用测试固定行为，再实现最小功能，并在提交前运行相应验证。任何阶段结束时均保持可构建、可测试。

## 10. 主要风险与处理

| 风险 | 处理 |
| --- | --- |
| 自绘控件影响无障碍 | 文本输入使用原生承载；自绘交互元素实现可访问名称、焦点和操作接口，并加入人工验收 |
| ARM64 环境不足 | CI 交叉编译；真实 ARM64 项保持待验收，获得设备后补充证据 |
| 置底行为受 Windows Z 序影响 | 采用非激活窗口与前台变化校正；不依赖未公开的桌面 WorkerW 技巧 |
| Toast 在便携版身份不足 | 安装版注册应用标识；便携版降级为托盘和窗口内提示 |
| 未签名安装包触发 SmartScreen | 发布流程预留签名；未签名版本明确标识，后续接入证书不改变产物结构 |
| 原版 localStorage 无法直接读取 | 保持 JSON schema 兼容，使用旧版导出/新版导入；不在主程序中重新引入浏览器依赖 |
| 原生重写引入行为回归 | 旧实现与测试作为行为基线，按模块移植并逐项对照需求验收 |

## 11. 完成标准

满足以下条件才可宣布原生迁移完成：

- 程序运行期间不存在浏览器、WebView、本地 HTTP 服务或 PowerShell 宿主。
- x64 与 ARM64 均能生成 `.exe`、安装包和便携包。
- 所有 P0 功能通过自动测试或对应 Windows 人工验收。
- 旧版 JSON 导出文件可被原生版正确导入。
- 原子保存、损坏恢复与七日备份均有故障测试证据。
- 置顶、置底、鼠标穿透和至少两条逃生机制在真实 Windows 环境通过。
- GitHub Release 工作流可从版本标签生成带校验值的产物。
- README、隐私说明、安装、升级、卸载和数据位置说明完整。
